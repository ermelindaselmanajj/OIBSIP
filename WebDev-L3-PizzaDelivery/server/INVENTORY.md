# Inventory and ingredient availability

`GET /api/admin/inventory` requires an authenticated administrator and returns `{currency:"EUR",items:[{id,name,category,stock,threshold,priceMinor,status,updatedAt}]}`. Status is `out-of-stock` for stock 0, `low-stock` for positive stock at or below the threshold, and `available` above the threshold.

`PATCH /api/admin/inventory/:id` requires an administrator. Send stock, threshold, or both as numeric nonnegative safe integers; zero is allowed. Unknown fields, numeric strings, fractions, invalid IDs and empty bodies receive 400. Missing items receive 404. Missing/invalid sessions receive 401 and valid user sessions receive 403. Database failures return a generic 500. This phase supports manual updates only and does not decrement stock.

`GET /api/ingredients` requires a verified user session. It returns `{currency:"EUR",ingredients:[{id,name,category,available,priceMinor}]}`, including out-of-stock items with available=false. It does not expose stock counts or thresholds. Administrators receive 403 for this user endpoint.

Categories are base, sauce, cheese and vegetable. Names are trimmed and internal whitespace is collapsed. A unique index on category and name prevents duplicate exact options. Stock and threshold have schema validation for nonnegative safe integers.

Prices use integer euro cents: 100 cents = €1. Inventory records need `priceCurrency:"EUR"` and a nonnegative safe-integer `priceMinor`; unconverted or invalid prices appear as null and prevent quoting. Run `npm run seed-prices` manually to apply the EUR demo prices defined in `scripts/seedPrices.js` to known ingredients with missing/legacy currency or missing EUR prices. It preserves existing EUR prices, IDs, stock, thresholds and timestamps; repeated runs do not overwrite already-priced EUR records. Unknown ingredients remain unpriced. The stock/threshold update endpoint does not edit prices.

`POST /api/orders/quote` calculates current EUR prices and checks availability for quantities 1–10. `POST /api/orders` validates the quote fingerprint and uses a user-scoped idempotency key to persist one `pending_payment` snapshot across retries. Owned order summaries remain readable after refresh. Existing INR snapshots are preserved and marked `checkoutEligible:false`; users can rebuild their choices using current EUR prices. Pending orders do not reserve or decrement stock, and this phase does not process payment.

To populate the 20 builder options, manually run `npm run seed-inventory` from server/. It loads server/.env using an absolute path and initializes the unique index before inserting. New entries receive stock 50 and threshold 20. Existing entries, including edited stock, thresholds and timestamps, are preserved using only $setOnInsert. Repeated and concurrent runs do not overwrite or delete records. If legacy duplicates prevent the index, the script fails and reports a generic message; review those records manually. Failures after some inserts may leave a partial seed; rerunning safely fills missing options. Database connections are closed on success or failure. Never use the unrelated destructive pizza seed as an inventory seed.

The automated tests mock the database. Local verification also ran the seed against real MongoDB and confirmed that both inventory APIs returned all 20 ingredients with matching record IDs. The builder's response parser accepted the real API payload. An empty ingredient array means the inventory has no records; failed requests or malformed responses show an error with Retry.

The builder checks availability on refresh, when returning to the tab, and before advancing. Unavailable ingredients remain visible but disabled; selections that become unavailable are removed. Ingredient photos retain their original files and use consistent 4:3 frames with individual framing adjustments. All four categories were inspected in Chrome headless at desktop and mobile widths (1440, 390 and 320 pixels).

## Scheduled low-stock alerts

The backend starts a single node-cron task after MongoDB connects. It checks every 15 minutes in UTC by default; optional `LOW_STOCK_CRON` overrides the expression (for example, `0 * * * *` checks hourly). `LOW_STOCK_ALERTS_ENABLED=false` disables scheduling. No immediate startup email is sent. Restart the backend after changing these settings. Existing `MAILTRAP_HOST`, `MAILTRAP_PORT`, `MAILTRAP_USER`, and `MAILTRAP_PASS` are reused by the shared mail service.

Stock at or below the ingredient's threshold, including zero, needs restocking. Emails list ingredient names, categories, stock and thresholds, with a link to the admin inventory dashboard. Existing cards show `Low stock` or `Out of stock`; both conditions qualify for an email.

Recipients come only from the Admin collection with `isVerified:true` and a valid email address. New admins default to false; legacy accounts without the field are also excluded. Admin login continues to work before verification. Login or manual account creation alone does not verify mailbox ownership. No existing account is automatically verified or assigned a different role.

### Verify an administrator email

Sign in at `/admin/login`, then use **Send verification email** in the inventory dashboard's Email alerts panel. `POST /api/admin/request-email-verification` requires an admin JWT and accepts no account details: only the signed-in account's stored email can receive the message. User JWTs receive 403, and unauthenticated requests receive 401. The mail uses the existing SMTP settings and links to `SERVER_URL/api/admin/verify-email/:token`. Opening the link consumes a 30-minute, single-use token, verifies that same account/email, and redirects to `CLIENT_URL/admin/login` with success or invalid/expired-link guidance. Sign in again or refresh the dashboard's email status to see **Verified**. Only this completed link flow can enable alerts; do not edit the verification flag manually.

The database stores SHA-256 hashes, never raw link tokens. An atomic 90-second send lock prevents simultaneous requests; successful deliveries have a 60-second resend cooldown. SMTP failures return 503, release the lock when possible and leave any previous accepted link valid. A crashed request's lock expires automatically, so the admin can retry. Delivery is reported only after SMTP accepts the account's address; acceptance does not prove inbox delivery. Tokens and internal delivery fields are excluded from account profiles and never logged. Verification does not change login permissions, passwords, roles, inventory, orders or payment state.

If your SMTP host is Mailtrap Sandbox, open the captured message in the Mailtrap testing inbox to exercise the local flow. Sandbox capture is not actual delivery to the administrator's mailbox; proving ownership of the real address requires an SMTP service that delivers there, using the existing SMTP variable names. No automated tests send real emails.

`npm run test:admin-verification:integration` uses a new isolated `pizza_admin_verify_test_*` MongoDB database, fixture admin/user accounts and simulated SMTP. It checks JWT role restrictions, single-use/expired links, cooldowns, concurrent requests, SMTP retry, account-email binding, login compatibility and eligibility for low-stock alerts. Only the generated test database is dropped at cleanup.

Each ingredient has an internal `lowStockAlertEpisode`. A separate `stockalertdeliveries` collection stores ingredient, episode, recipient and `sentAt` only after SMTP accepts that recipient. Already notified recipients are skipped on later runs and after a restart. Failed recipients can retry independently, while newly verified recipients can receive the currently active alert. Manual inventory updates atomically clear the episode when stock rises above the threshold (or a threshold change resolves the condition), even if stock falls again between scheduled runs. The scheduler also detects restocks made outside the API when it observes them. Counts, prices and order/payment state are never changed by the scheduler; alert metadata does not update the ingredient's `updatedAt`.

The task uses node-cron's `noOverlap` option and a checker guard. Run this scheduler in a single backend process; multiple independent replicas require a distributed lock. SMTP acceptance is not proof of inbox delivery. SMTP and MongoDB cannot commit atomically: a process crash or database failure after SMTP acceptance but before saving `sentAt` can cause a retry to send a duplicate. Normal scheduled runs and restarts after a saved delivery do not resend. No delivery history is deleted automatically.

`npm test` runs offline regression tests. `npm run test:stock-alerts:integration` uses the existing MONGO_URI to connect to a **new random `pizza_stock_alert_test_*` database**, always uses simulated SMTP, and drops only that test database afterwards. It does not start the scheduler, send real emails, or read/write production inventory/accounts/orders. The database user needs permission to create and drop this isolated database. If interrupted forcibly, a leftover database with that prefix may need manual cleanup.
